# 总体架构设计

## 项目概述

**pascc**（Pascal-S to C Compiler）是一个将 Pascal-S（教学用简化 Pascal）源程序翻译为 C 语言代码的编译器，作为《编译原理与技术课程设计》的课程项目。项目采用经典的 **4 阶段编译流水线**架构，以 C++17 为核心语言，集成 Flex 词法生成器和 Bison 语法生成器（均来自 WinFlexBison 工具链），使用 CMake 3.16+ 作为跨平台构建系统。

项目的设计核心理念是**模块独立性**与**流水线可编排性**。四个编译阶段（词法分析、语法分析、语义分析、代码生成）各自作为独立模块运行，由 `CompilerDriver` 统一编排调用顺序，阶段之间通过明确的数据结构（`LexerResult`、`ParserResult`、`SemanticResult`、`CodegenResult`）传递信息和错误。这种设计使得每个模块可以独立测试、独立调试、独立演化。

## 编译流水线

整个编译过程从 Pascal-S 源文件（`.pas`）到 C 目标文件（`.c`），依次经过四个阶段，由 `CompilerDriver::run()` 统一编排。下图展示了完整的编译流水线架构和各阶段间的数据传递关系。

![编译流水线架构图](picture/01-architecture-pipeline.png)

上图清晰地展示了四个阶段的输入/输出格式和流转方向：

- **词法分析阶段**（`Lexer`）：接收原始 Pascal-S 源代码字符串（`.pas` 文件内容），通过 Flex 生成的确定性有限自动机（DFA）扫描，输出 Token 流（`std::vector<Token>`）及词法错误列表（`std::vector<LexError>`）。Token 流是后续所有阶段的唯一输入数据源。Flex 扫描器内部维护行号 `g_line`、列号 `g_col` 全局状态，每匹配一个词素即通过 `EMIT_TOKEN()` 宏记录位置并返回 Bison Token 整型码。
- **语法分析阶段**（`Parser`）：接收词法分析器输出的 Token 流，通过 Bison 生成的 LALR(1) 解析器进行自底向上的移进-归约分析，验证程序是否符合 Pascal-S 文法。Bison 使用 `%left`/`%right` 指令声明运算符优先级与结合性。若语法正确则返回一个占位性质的 AST 根节点（`shared_ptr<ProgramNode>`）；若有语法错误则通过 `yyerror()` 回调收集 `std::vector<ParseError>`。
- **语义分析阶段**（`SemanticDeclarationAnalyzer`）：接收 Token 流和语法分析结果（`ParserResult`），对 Token 流做独立的递归下降遍历，构建作用域栈（`ScopeStack`）和符号表体系（`TableSet` 链表），执行标识符声明前使用检测、同一作用域内重复定义检测、类型兼容性检查（含 `isNumeric()`、`isAssignable()`、`promoteNumeric()` 等规则）和过程/函数调用的参数数量与类型匹配检查。
- **代码生成阶段**（`CodeGenerator`）：接收原始输入文件路径（而非 Token 流——模块内部重新调用 Lexer），对 Token 流做两次递归下降扫描（第一遍收集函数名和 VAR 参数信息；第二遍执行逐结构翻译），直接输出等效的 C 语言源代码字符串（`CodegenResult.cSource`）。

`CompilerDriver` 作为编排者位于流水线底部，通过虚线箭头连接到四个阶段，负责按序调用、错误检查和文件 I/O 管理。

- **输入**：`.pas` 后缀的 Pascal-S 源文件
- **输出**：同名 `.c` 后缀的 C 语言源文件
- **命令行**：`pascc -i <input.pas>`

- **实现层（src/）**：包含各模块的具体实现逻辑。其中 `compiler_driver.cpp`（106 行）实现流水线编排，`code_generator.cpp`（1481 行）实现全部代码生成逻辑，`semantic_declaration.cpp`（992 行）实现全部语义分析逻辑。各实现文件的内部结构均采用匿名 `namespace {}` 隐藏内部实现细节，仅通过公开头文件暴露最小接口。

## 核心数据结构总览

整个编译流水线中，以下数据结构构成了模块间通信的"通用语言"。每个阶段将其分析结果封装在对应的 Result 结构体中，同时携带错误信息。

![核心数据结构 UML 类图](picture/10-core-data-structures.png)

上图以 UML 类图的形式展示了贯穿整个编译流水线的核心数据结构的层次关系：

- **`SourcePosition`**（定义于 `token.h:76-80`）：所有位置信息的原子类型，包含 `line`（int，初始值 1）和 `column`（int，初始值 1）两个整型字段，用于错误定位和 Token 溯源。
- **`Token`**（定义于 `token.h:82-86`）：词法分析的基本输出单元，包含三个字段：`type`（`TokenType` 枚举）、`lexeme`（`std::string` 类型，已做 ASCII 小写化处理）、`pos`（`SourcePosition` 类型的起始行列号）。词法分析器在 Flex 规则动作中通过 `EMIT_TOKEN(code, lexeme)` 宏构造 Token 并记录位置。
- **`LexError`** / **`LexerResult`**（定义于 `lexer.h:9-14, 16-21`）：词法分析阶段的输出结构体。`LexError` 包含 `code`（如 `"E106"`）、`message` 和 `pos`；`LexerResult` 通过组合关系持有 `std::vector<Token>` 和 `std::vector<LexError>`。
- **`ParseError`** / **`ParserResult`**（定义于 `parser.h:8-13, 15-20`）：语法分析阶段的输出。`ParserResult` 包含 `errors` 向量和 `root`（`std::shared_ptr<ProgramNode>` 类型的 AST 根节点，当前为占位空节点）。
- **`SemanticError`** / **`SemanticResult`**（定义于 `semantic_declaration.h:6-11, 13-17`）：语义分析阶段的输出，仅包含 `errors` 向量（语义分析不产出新的中间表示，只做验证）。
- **`CodegenResult`**（定义于 `code_generator.h:6-10`）：代码生成阶段的输出，包含 `ok`（bool）、`message`（std::string）和 `cSource`（std::string，完整的 C 语言源代码）。

注意所有错误结构体（`LexError`、`ParseError`、`SemanticError`）都共享相似的字段模式（`code` + `message` + `pos`），但在代码中它们是独立定义的结构体而非通过继承关联——这是为了保持各模块的完全独立性。

## 核心数据流

```
main.cpp
  └→ CompilerDriver::run(inputPath)                      [src/compiler_driver.cpp:14]
       ├─ 1. 检查输入文件扩展名是否为 .pas（大小写不敏感）    [src/compiler_driver.cpp:15-18]
       ├─ 2. 检查文件可读性并读取全部内容到内存字符串          [src/compiler_driver.cpp:20-28]
       ├─ 3. Lexer::tokenizeDetailed(source) → LexerResult  [src/compiler_driver.cpp:30-39]
       │     └─ 内部：重置 Flex 状态 → 创建扫描缓冲区 →
       │        循环 yylex() → mapBisonTokenToInternal() →
       │        释放缓冲区 → 追加 EndOfFile 哨兵 Token
       ├─ 4. Parser::parse(lexResult.tokens) → ParserResult [src/compiler_driver.cpp:41-49]
       │     └─ 委托给 parseWithBison() → 设置全局 Token 指针 →
       │        yyparse() 执行 Bison LALR(1) 解析
       ├─ 5. SemanticDeclarationAnalyzer::analyze(tokens, parserResult) → SemanticResult
       │     └─ 内部：创建全局作用域 → 注入内建类型 →
       │        递归下降遍历 Token 流 → parseProgram() → parseBlock() →
       │        逐子程序解析 + 表达式类型推导
       ├─ 6. CodeGenerator::generateTemplate(inputPath) → CodegenResult
       │     └─ 内部重新调用 Lexer → 解析全局常量/变量 →
       │        第一遍扫描收集函数信息 → 第二遍扫描翻译语句 →
       │        Emit C 源文件字符串
       └─ 7. 写入输出 .c 文件并打印统计信息（Token 数量、各阶段状态）
```

## 模块间接口契约

以下接口契约图精确描述了四个核心模块的公开函数签名、参数类型和返回类型，以及数据在模块间的流动方向。

![模块间接口契约图](picture/10-module-interfaces.png)

该图揭示了几个重要的设计细节：

1. **数据传递路径**：Lexer 产出的 `LexerResult.tokens` 被 Parser 消费（通过 `parse(const std::vector<Token>&)` 传递），也被 Semantic 消费（通过 `analyze(tokens, parserResult)` 传递——Semantic 同时需要 tokens 和语法验证结果作为前提条件）；CodeGenerator **不接收** tokens 参数——它的公开接口 `generateTemplate(const std::string& inputPath)` 只接受文件路径字符串，模块内部在 `code_generator.cpp:1311-1322` 处重新独立调用 `Lexer::tokenizeDetailed()`。这意味着 CodeGenerator 拥有自己独立的词法分析结果，与 Driver 中的 tokens 是完全独立的两个 `vector<Token>` 副本。这种设计使 CodeGenerator 可以完全独立于编译流水线运行（参见测试体系中的 `codegen_template_tests`，它直接调用 `CodeGenerator::generateTemplate()` 而不经过 CompilerDriver）。

2. **只读语义**：Parser 和 Semantic 对 tokens 向量只有只读访问权限（通过 `const std::vector<Token>&` 传递），不会修改词法分析的结果。这保证了 Token 流在整个流水线中的不变性。

3. **错误传播机制**：每个阶段将其错误累积在各自 Result 结构体的 errors 字段中，Driver 在每个阶段完成后检查 `errors.empty()`，若不为空则通过 `logutil::error()` 逐条输出错误信息到 stderr，然后立即终止流水线并返回对应退出码（`ErrorCode::LexicalError = 7`、`ErrorCode::SyntaxError = 8`、`ErrorCode::SemanticError = 9`、`ErrorCode::GenerationError = 10`）。

4. **CodeGenerator 的自循环**：由于 CodeGenerator 内部重新调用 Lexer，它形成了一个"自给自足"的微型流水线。这种设计的代价是词法分析被执行了两次（一次在 Driver 中，一次在 CodeGenerator 中），但换来了模块间的完全解耦。

## 重要架构决策

### 1. 两套解析器并存 —— "验证-翻译分离"

项目同时拥有两个解析器，但它们承担完全不同的职责：

- **Bison 解析器**（`parser_bison.y` 343 行 + `parser_bison_bridge.cpp` 127 行）：负责**语法正确性验证**。它使用 Bison 从 `.y` 文法文件生成的 LALR(1) 自动机对 Token 流进行移进-归约分析，遵循 Pascal-S 标准文法（共定义约 70 条产生式），验证程序是否符合语法。Bison 使用 `%left T_OR`、`%left T_PLUS T_MINUS`、`%left T_MULTIPLY T_DIVIDE T_DIV T_MOD T_AND`、`%right T_NOT` 四层优先级声明来处理表达式中的运算符优先级和结合性。语义动作中**不构建有意义的 AST**——仅当 `yyparse()` 返回 0（成功）时，在 `parseWithBison()` 中创建一个空的 `ProgramNode` 占位符（见 `parser_bison_bridge.cpp:118` 注释："M3 minimal AST placeholder: full node construction will be added in M4 semantic actions"）。

- **手写递归下降代码生成器**（`code_generator.cpp` 约 1480 行）：负责**代码翻译**。它**不使用** Bison 或任何自动生成的解析器代码，也**完全不使用** AST（`ast.h` 中定义的 `ProgramNode`/`StatementNode`/`ExpressionNode` 在代码生成路径中从未被引用）。代码生成器直接对 Token 流做手写的递归下降模式匹配，通过 `parseExpressionUntil()`、`parseSingleStatement()` 等函数逐个识别 Pascal 语法结构并生成等效 C 代码。

这种"验证-翻译分离"的设计使语法错误的精确检测（Bison 的 LALR(1) 分析能精确报告错误位置和期望的 Token）与灵活的代码翻译逻辑（手写的递归下降可以方便地处理 VAR 参数解引用、多维数组下标逗号替换、无括号函数调用补全等特殊转换）完全解耦，各自可以独立优化和调试。

### 2. AST 仅作占位

`ast.h`（48 行）中定义了 `AstNode` 抽象基类及其三个派生类：

```cpp
enum class AstKind { Program, Statement, Expression };

class AstNode {
    AstKind kind_;
    std::vector<std::shared_ptr<AstNode>> children_;
public:
    void addChild(std::shared_ptr<AstNode> child);
};

class ProgramNode    : public AstNode { /* 无额外字段 */ };
class StatementNode  : public AstNode { /* 无额外字段 */ };
class ExpressionNode : public AstNode { /* 无额外字段 */ };
```

当前 AST 节点仅含 `kind_` 枚举和 `children_` 列表，**未填充任何具体信息**（如运算符类型、标识符名称、字面量值等）。Bison 的语义动作中所有产生式右侧的动作均为空（`{ }`），未向 AST 写入任何数据。AST 在当前实现中仅在 `ParserResult.root` 中作为一个"语法正确的信号"存在。它的完整构建留待后续开发阶段（如需要引入中间代码优化或多遍语义分析时）。

### 3. 语义分析独立工作

语义分析器（`semantic_declaration.cpp` 约 992 行）完全独立于其他模块：

- 它**自己重新遍历 Token 流**（通过内部维护的 `pos_` 游标和 `advance()`、`match(type)`、`peekType(n)` 辅助函数），不依赖 AST 也不依赖 Bison 解析结果。
- 它使用**独立的符号表体系**：`ScopeStack`（基于 `std::vector<std::unique_ptr<TableSet>>` 的栈结构）管理嵌套作用域，`TableSet` 通过 `prevSet_` 指针形成单向链表实现链式查找，`BuiltinTypePool` 管理四种内建类型（integer/real/boolean/char）的单例。这套符号表体系与代码生成器的内部数据结构（`ConstDecl`/`VarDecl`/`RoutineDecl` 等）完全独立。
- 它不依赖代码生成器，代码生成器也不依赖语义分析器的结果（语义错误由 Driver 在流水线中通过 `if (!semanticResult.errors.empty())` 检查拦截，代码生成器只在语义通过后才被调用）。

### 4. 代码生成采用"直译"策略

代码生成器（`code_generator.cpp` 1481 行）对 Token 流做递归下降模式匹配，逐结构翻译为等效 C 语法。核心翻译策略包括：

- **类型映射**：Pascal `integer` → C `int`，Pascal `real` → C `float`，Pascal `boolean` → C `int`（C 无原生 bool，语义上用 1/0 替代），Pascal `char` → C `char`。映射函数 `mapTypeTokenToC()`（`code_generator.cpp:70-78`）通过 switch-case 实现。
- **控制流映射**：`for i := A to B do` → `for (i = A; i <= B; ++i)`；`for i := A downto B do` → `for (i = A; i >= B; --i)`；`repeat stmts until C` → `do { stmts } while (!(C))`；`case expr of` → `switch (expr)`；`if C then S1 else S2` → `if (C) { S1 } else { S2 }`。
- **VAR 参数处理**：Pascal 的 VAR 引用参数在 C 中被翻译为指针传参，在声明、读取（表达式内自动解引用 `(*paramName)`）、写入（左值 `*paramName =`）、传参调用（实参加 `&`）四种场景下做不同处理。
- **运行时 I/O 辅助**：自动生成 `pas_write_int()`、`pas_write_real()`、`pas_write_char()`、`pas_read_int()`、`pas_read_real()`、`pas_read_char()`、`pas_writeln()` 七个静态辅助函数，封装 `printf`/`scanf` 调用，确保 C 输出的行为与 Pascal I/O 语义一致。
